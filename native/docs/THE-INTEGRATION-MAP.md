## Vocabulary (the owner, 2026-11-24, relayed by the ingestion session; the owner's latest wording is "the Corpus, the scholia, and the formicary"; nothing decided beyond this)
- **The corpus** is the texts (Zenodotus). **The scholia** are the middle layer: notes in the margin of a text, by address, without carrying the text; **Ýlir-One is the first instance of the scholia** (the name of this instance, not of the layer: if the owner means otherwise he will say). **The formicary** (an ant nest, Latin *formica*) is the third layer, bound to specific users: "a stigmergic construction", like what ants and termites build, marks left in the environment that guide the next action. **Nothing is built or decided about the formicary's contents.** The attention notes in `eodb-clone/facade/SIG.md` and `pharos/eoql/SIG-ANSWER.md` already say how such marks must behave: a pointer with no value, presence can only cause more looking, absence proves nothing. The owner's clarification applies: it records the repos' own activity for that user, not agents' notes. For this map: the nearest things that exist are the chat's remembered corrections (kind `correction`, by name, per log) and the trail marks of fork 2's trail store; whether they become the formicary is the owner's.

**One canonical name per layer, and aliases (the owner's addendum, relayed).** CANONICAL: **corpus**, **scholia**, **formicary**. ALIASES: the scholia may be called "the model"; the formicary may be called "the log", "the shadow", "the impression", "the trails", "the pheromone trails", and more. The ingestion session's caution, which this map follows: "the log" already means a pharos log in the nexus (Ýlir-One's own, fold-demo, the khora gate log) and "shadow" already means a stand-in that shadows the real priors (and the chat's "shadow read" is a third use: a comparison run of the chat's reading beside the canonical read, nothing to do with the layer), so **code, log kinds and file names use the canonical names only; the aliases are for prose.**

## What "the real pipeline" is
One call reads a document: `readToWeft` (`native/the-fold/read-process.mjs`), the same as `readDocument` (`native/reading.js`), held equal by `native/tests/one-door.test.mjs`. It reads whole and in order through the language's priors (`prior-source.mjs`) and the canonical options (`canonicalReaderOptions`: pronoun presence, name personhood, case-marked clauses, a **gender prior chain**), and emits a `WeftEntry@4` (cast with every mention's address, edges, vocabulary, pronouns, the SEG+EVA cut, gaps). Every read writes one entry to pharos and a read with a missing capacity is refused unless it says it is degraded. The guards are `native/tests/reading-baseline.test.mjs` (the reading-critical files hash to the recorded baseline; re-record only after measuring), `one-door.test.mjs`, and the typed gaps. No model. (`native/docs/THE-READING-PIPELINE.md`, `CLAUDE.md`.)

## A finding that decides how the chat can use the canonical read (measured 2026-11-24, this machine)
`reading.js readDocument` on a two-sentence text takes about 0.5 s with `PHAROS` and `PHAROS_CHATTER` pointing at empty directories, 0.4 s with `KHORA_NO_PHAROS_GATE=1`, and **30 to 105 seconds** in the default environment: `assertPharos()` alone took 105 s once and 30 s with only `PHAROS_CHATTER` overridden; with `PHAROS` set to any directory (`~/.pharos/default`, `~/.pharos`, or a temporary one) it takes 12 to 18 ms. A first canonical read I started on the real priors ran for 15 minutes. The cause is in the log the gate opens when `PHAROS` is unset: `~/.pharos/khora` is **294 per-process `.jsonl` files, 119 MB**, one per process that ever read through the gate, and `pharos/lib/gate.mjs` opens it (`P.open`, `P.status(h)`, `P.entries(h)`), which reads every file. So the cost is per process and grows with every process that reads. A long-running server pays it once at its first canonical read; every probe, test and one-off script pays it each run. The chat's own server does not go through the gate today. **The cause, measured by the ingestion session on a COPY of the log (294 files, 103 MB, 214,481 entries; the real log untouched; the machine was heavily loaded, so trust the split and the linear growth, not the seconds):** one process pays three whole-directory reads before any reading: `P.open()` loads every writer file only to check whether a frame exists (14.3 s), `P.entries()` builds the view (26.5 s), and the gate's `P.status(h)` builds the view again and runs `findConflicts` (45.6 s, 1,075 conflicts found): about 87 s, which matches my 105 s. A second handle in the same process re-reads everything (the cache is per handle). The cost grows with ENTRIES, not files, so merging the 294 files would not fix it by itself, and the hash chain is not a reason: it is per writer file and only in `.phb` files, and this log is JSONL. **Cheap fixes, all in the pharos repo (nobody has changed anything):** drop `P.status(h)` from `gate.mjs` line 50 (the next call, `fs.accessSync(h.dir, W_OK)`, already proves the log is writable and nothing in the gate uses the counts); make `open()` stop at the first writer file that holds a frame; in `record()` (`gate.mjs` line 89, `P.entries(h).some(kind declared)`, the same scan once per process per kind) check the kind in this writer's own file or keep a per-process memo. **The structural answer already exists in the nexus:** the lazy placed store (pharos ledgers pharos-lazy A9/A10, `DB_STORE=lazy` in the eodb facade), where a write never loads the log and one address read took 50 ms at 100,000 entries; a gate log that gains one file per process is exactly the log that needs it. **Not done:** I have not changed the pharos repo or moved any log, and I have not set `PHAROS` for anyone. The owner decides where reads are logged and which fix. **Settled:** the 12-CPU-minute run on a 28 KB document was the gate on the default log; with a temporary log the canonical read took about 6 s on a 5,000 to 9,000-character text (below). That is slow for a novel (100 to 255 s, and a heap that ran out on Shakespeare) but short enough for a chat thread of a few hundred characters.

## The canonical read, made fast (the owner: "fix the canonical read, we need it all fast"; local commits, nothing pushed, 2026-11-24)
**The design the owner gave: schemas first, then read backward to get the current state, and read only what is relevant.** A log's schema is its frame and its kind declarations; the data is read against it, newest first, matching lines only, and stops when the question is answered. Pharos did the opposite: every question (does the frame exist, is this kind declared, what is the frontier for a write) built the whole view of the log.
**Where the time went, and what was done (EXPLORATORY: one machine, under load; trust the split):**
- **The pharos gate, 87 to 105 s per process on the real 294-file, 214,481-entry log, then minutes per document:** `open()` loaded the whole directory to ask whether the frame exists (14 s); the gate's `status()` built the view and every conflict to prove the log opens (45 s); `record()` and `weaveFullRead` built the view to ask whether a kind was declared (26 s each) and wove each being, edge and binding one at a time, each `weave` building the view again for its frontier. Fixed in the pharos repo on the local branch `fast-gate` (worktree `pharos-fast`, commits 7afe181 and 776269b, 89 pharos tests pass): `foldBack` (newest file first, each file from its end, raw bytes, the hit confirmed on its line, stop at the answer: `hasFrame`, `hasKind`, `missingKinds`), `weaveUnchained` (one entry, no view), `schema`, `recent`, `current` (the latest entry per address, retractions skipped; agrees with the full view on all six kinds of a copy of the real fold-demo log, 8 to 24 ms against 388 ms). And in khora (998b569): `weaveFullRead` and `weaveReferents` write one bulk append and find the missing kinds by one backward fold. On a COPY of the real log: `assertPharos` 157 ms (was 30 to 105 s), the first `recordRead` 1.2 s, later ones 150 ms.
- **The read's own first-run cost, 8.6 s of which 3.9 s was the language identifier** rebuilding its n-gram model from the priors in every process, because `extractSurfacesHeard` ignored the read's declared language and detected it again from the text. It now takes the settled language (27c3154); output byte-identical on three texts (the sha256 of the whole weft); three reads in one process 8.3 s to 2.8 s. What is left of the first run: the parser lexicon load (1.2 s), the prior JSON (0.75 s), the English parser model (0.6 s).
- **After all the fixes (2b7b460 adds a remembered priors-directory listing: every `grammarFor`/`stemOf` listed the 1,957-file directory, 1.15 s of a 12 s read; output byte-identical on three texts), the whole canonical read of a 9,000-character document in a FRESH process, EXPLORATORY, machine load about 12:** gate off 2.9 s first, 0.35 s after; gate on against a copy of the real 294-file log 3.7 s first (the gate adds 0.85 s, which includes writing the whole read), 0.65 s after. Before: 87 to 105 s for the gate alone, then minutes per document, and 8 to 11 s for the read's own first run. What is left is the parser: 3.0 s of the 12 s profile of 120,000 characters is `ud-parser.js` and 2.2 s `english-parser.js` (the work itself), plus about 1.5 s of one-off model loading.
- **The one behaviour change of 27c3154, checked at Parsing fixes' request (EXPLORATORY, four texts, the whole weft compared before and after):** where the declared language differs from the text's the output is the same for a French text declared English, an English text declared French (typed gaps `no_morphology`, `no_dotted_prior` both ways) and the English control; it differs for a MIXED English and French text declared English: the cast (named beings) and the rows are the same, but the `heard` surfaces (the caseless tier) differ (before, the text-detected grammar admitted "and" as a heard being; after, the declared English one admits "village"), one edge fewer, and five `quality` fields move. So the change is: a read with a declared language reads its heard surfaces in that language, and it only shows on a text that mixes languages. A caller that does not declare a language still has it heard from the text.
- **Steady state:** about 27 microseconds per character, linear (50,000 characters 1.3 s, 200,000 characters 5.4 s, warm; peak memory about 890 MB at both sizes, so it is the priors and not the text). A novel of 900,000 characters is about 25 s warm; War and Peace about 90 s. The streamed rows-only read is about 4 times faster and computes no cast, edges or surprise. Not profiled yet (the profile run was killed when the machine restarted).
- **`current()` is linear in entries (the ingestion session, on the 17,463-entry Ýlir-One log):** about 100 ms per read by address when the entry sits early in the log, against 0.25 ms for a lookup in the sidecar and 6.6 to 21.9 s per `heads()` lookup at 101,000 entries (loaded machine). So it is right for a single catalog or gap lookup by address and not for a per-word layout (about 12 s per lookup at 2 million entries): words stay in the sidecar.
- **Needs, and where it stands:** khora's gate uses the new pharos calls when they exist and falls back to the old ones when not, so khora is safe on an old pharos but only fast on the new one. With the owner's yes (2026-11-24) the pharos branch `fast-gate` was fast-forwarded into the LOCAL pharos main (a79ed70 to 776269b, 89 tests pass on main); it is not pushed. `assertPharos` on the real default log with no overrides: 128 ms.

## The ingest itself ran beside the canonical read (the ingestion session, 2026-11-24)
The biggest piece of reading in the nexus did not go through `readToWeft`: the canonical door took 100 to 255 s per novel, ran a 1 GB heap out on Shakespeare, and `readInOrder` did not complete when called directly, so the ingest uses the reader's own splitter and parser, streamed. The ingestion session then checked it, at one reader version (khora-smell ccf2033, the real priors, English; EXPLORATORY, two documents): the canonical read (`readDocument(text, { language: "eng", rows: true })`, `PHAROS` and `PHAROS_CHATTER` set to empty temporary directories) and the streamed read (`abbreviationsFor` + `splitSentences` + `rowsOfFor(...).rowsOf`, one sentence at a time) gave **identical rows**: Lincoln's Second Inaugural, 33 of 33 sentences and 969 of 969 rows; a 9,000-character Dracula excerpt, 86 of 86 sentences and 1,878 of 1,878 rows, each compared on text, row count and each row's lemma, upos, kāraka, head and deprel. With a temporary log the canonical door cost 6.9 s and 5.7 s against 0.1 s streamed (about 60 times). **What "equal" means and does not:** equal rows, which is all the ingest records; the canonical read also computes the cast, edges and surprise that the streamed read does not; and the streamed read calls the same parser on the same sentence cuts, so the check tests the cut, the abbreviation handling and the door's own options, not the parser. Not tested: long documents (an abbreviation table learned from a whole novel), other languages. So "equal on rows in two short documents", and a standing check of a handful of documents per language at each reader change would hold it. The 12-CPU-minute run that began the question was the gate on the default log, not the read. That makes the performance and robustness of the canonical door the common blocker: the pharos gate's per-process cost (above) is one part; the per-novel time and the heap are another. **Owner's choice (not made):** make the canonical door fast and bounded enough that the ingest and the chat can use it, or declare the streamed reader the way large texts are read and hold it equal to the canonical one by a standing check.
